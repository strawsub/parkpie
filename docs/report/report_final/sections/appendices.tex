\subsubsection{Prerequisites}
\begin{itemize}[noitemsep]
  \item Git (to clone repository).
  \item Flutter SDK (recommended: Flutter 3.x or newer). Ensure \texttt{flutter} is on PATH.
  \item Android SDK / Xcode (for mobile targets) if you plan to run on device or simulator/emulator.
  \item Java 21
  \item Gradle 8.14.3 (included via wrapper)
  \item An RDBMS if the backend requires one (PostgreSQL, MySQL, etc.) — check backend configuration.
  \item Optional: Docker / docker-compose if you prefer containerized runtimes.
\end{itemize}

\paragraph{Identify project layout}
Open a terminal in the repository root and locate Flutter and Spring Boot modules:

\begin{verbatim}
# from repo root
# find Flutter project (look for pubspec.yaml)
find . -maxdepth 3 -name "pubspec.yaml"

# find backend (look for build.gradle, settings.gradle, or pom.xml)
find . -maxdepth 3 -name "build.gradle" -o -name "pom.xml" -o -name "settings.gradle"
\end{verbatim}

Typical results:
\begin{itemize}
  \item Flutter app folder contains \texttt{pubspec.yaml}.
  \item Backend folder contains \texttt{build.gradle} or \texttt{pom.xml} and \texttt{src/main/java}.
\end{itemize}

Replace the folder names in the commands below with the actual paths you found (examples: \texttt{frontend/}, \texttt{app/}, \texttt{backend/}, \texttt{server/}).

\subsubsection{Backend (Spring Boot) — build \& run}

\paragraph{Compilation}
Navigate to the backend directory and build the project:
\begin{verbatim}
cd apps/backend
./gradlew build
\end{verbatim}

On Windows:
\begin{verbatim}
cd apps\backend
gradlew.bat build
\end{verbatim}

\paragraph{Running the Application}
Start the backend server:
\begin{verbatim}
./gradlew bootRun
\end{verbatim}

On Windows:
\begin{verbatim}
gradlew.bat bootRun
\end{verbatim}

The server will start on \texttt{http://localhost:8080}. Database connection is pre-configured to Azure PostgreSQL.

\paragraph{Deployment}
The backend is deployed to Azure App Service at \texttt{https://parkpie-90018.azurewebsites.net}. The frontend application uses this Azure deployment by default, so no local backend setup is required for running the Flutter app.

flutter build web

The Flutter app will call the backend API. Locate where the base API URL is configured (common places: \texttt{lib/constants.dart}, environment files, or flavors). Example replacements:
\begin{verbatim}

\subsubsection{Sensor Data Processing and GPS Calculations}

\paragraph{Kalman Filter}
The Kalman gain is computed as $k = \frac{p}{p + r}$, where, $p$ denotes the estimation error (uncertainty in the estimate), and $r$ is the measurement noise. Before each update, the estimation error is predicted as:
$p' = p_t + q$
and then updated:
$p_{t+1} = (1 - k)p'$
, where $q$ represents the process noise. This filtering process yields smoother and more accurate GPS trajectories by balancing prior estimates with new observations. 

For inertial sensors (IMU), consisting of accelerometer and gyroscope, Kalman filters are applied to each axis ($x$, $y$, $z$), then combined using Euclidean norm $\sqrt{x^2 + y^2 + z^2}$. The filter parameters ($q$ and $r$) are tuned differently as accelerometer has less noise compared to gyroscope. 

\paragraph{Haversine distance calculation}

To compute distances between GPS coordinates on the Earth's surface, the Haversine formula is employed. It accounts for the Earth's spherical shape, providing accurate great-circle distances compared to simple Euclidean calculations.

Given two points $(\phi_1, \lambda_1)$ and $(\phi_2, \lambda_2)$ in radians, the Haversine formula computes:

\[
a = \sin^2\Big(\frac{\phi_2 - \phi_1}{2}\Big) + \cos(\phi_1)\cos(\phi_2)\sin^2\Big(\frac{\lambda_2 - \lambda_1}{2}\Big)
\]

\[
c = 2 \, \text{atan2}(\sqrt{a}, \sqrt{1-a})
\]

\[
\text{distance} = R \, c
\]

where $R = 6371~\text{km}$ is the mean Earth radius, and $\phi, \lambda$ denote latitude and longitude, respectively. This method ensures accurate geodesic distance measurement between coordinate pairs (cf. straight-line Euclidean distance).

\paragraph{Hysteresis threshold design}

ParkPie employs hysteresis to prevent rapid state switching when sensor readings fluctuate near thresholds.

\begin{itemize}
    \item Accelerometer hysteresis: dual entry and exit thresholds create a dead zone. This Schmitt trigger logic reduces rapid toggling.
        \[
        \text{RMS: } < 0.40~\text{m/s}^2 \text{ to enter ``still'', } > 0.45~\text{m/s}^2 \text{ to exit}
        \]
        \[
        \text{Quiet ratio: } \ge 70\% \text{ to enter, } < 58\% \text{ to exit}
        \]
    \item GPS hysteresis: a single speed threshold is combined with temporal requirements. Brief speed fluctuations do not trigger state changes.
        \[
        \text{Speed threshold: } 2.78~\text{m/s}, \quad
        \text{Driving: } \ge 10~\text{s and 20~m}, \quad
        \text{Parking: } 4-6~\text{s}
        \]
    \item State machine hysteresis: The multi-state logic enforces hysteresis: minor stops require sustained conditions (gyro spike, Bluetooth disconnect, or 60~s timeout) to trigger parking detection, and once parked, sensor noise is ignored.
\end{itemize}
