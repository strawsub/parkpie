We use BLoC (Business Logic Component) state management, which is a widely adopted architecture for production-level Flutter apps. BLoC separates state, events, and business logic, allowing for clear, maintainable, and testable code.
\begin{itemize}
    \item State represents the current condition of the app.
    \item Event represents something that happens (e.g., user action or sensor update).
    \item Bloc listens to events, applies business logic, and emits new states.
\end{itemize}

BLoC exposes a stream of states, to which Flutter widgets can subscribe. For instance, in the parking detection feature, each sensor BLoC (accelerometer, gyroscope, Bluetooth, GPS) emits a sensor state. The ParkingBloc listens to these sensor states, processes votes, and emits a new ParkingState. The UI then rebuilds automatically, for example displaying a “Parking detected” popup.

This separation of concerns ensures testable components and reactive UI updates. The BLoC pattern is conceptually similar to Swift’s MVVM architecture. In cases where logic is simple, we can use the lighter-weight Cubit, which omits events and allows direct state changes. Front-end directory is organised by key features: \texttt{map}, \texttt{camera}, \texttt{parking status detection}, \texttt{timer}.

To maintain consistent logic throughout development, we implemented unit tests for each major BLoC component, using mock service where required. These tests, together with linting checks, are integrated into our CI/CD GitHub pipeline and run on every commit to ensure consistent code quality and style.

\subsubsection{Backend}

The backend is organized into clear, responsibility-focused packages: \texttt{admin}, \texttt{parking}, \texttt{core}, and \texttt{api}, keeping Spring components small, readable, and easy to navigate.

Service and repository classes use intent-revealing method names, for example:
\begin{itemize}
    \item \texttt{ParkingSignService.ingestUserSign}
    \item \texttt{ParkingRestrictionDurationService.calculateDuration}
\end{itemize}

DTOs such as \texttt{UserSignIngestDto} and \texttt{ParkingSignDto} encapsulate request and response payloads and use Jakarta validation annotations to prevent malformed data from entering the database. The entire backend is documented with JavaDoc, and every API endpoint has OpenAPI (Swagger) documentation, for example:
\begin{itemize}
    \item Duplicate-detection heuristics in \texttt{ParkingSignService}
    \item Database bootstrapping and manual zone reconciliation in \texttt{DbPolishRunner} 
\end{itemize}

A comprehensive test suite ensures correctness and consistency:
\begin{itemize}
    \item Unit tests: Verify complex calculations, e.g., parking restriction duration validates time-window algorithms across edge cases
    \item Controller tests: Assert HTTP contracts and security filters
    \item Integration tests: Check that data storage and location-based queries work correctly with a PostGIS database using Testcontainers. For example, the \texttt{ParkingSignRepositoryIntegrationTest} runs with data loaded from postgis-init.sql.
\end{itemize}

Operations also gain leverage from the Spring Boot admin dashboard, which enables CSV imports, scheduler toggles, and live health monitoring. \subsection{Sensors}
\label{subsec:sensors}

Sensors are used in two different scenarios:

\begin{enumerate}
    \item \textbf{Detect that a travelling vehicle has parked}: GPS sensor provides macroscopic motion information through velocity and displacement measurements; the accelerometer captures microscopic vibration patterns that distinguish driving from stationary states; the gyroscope detects rotational signatures indicating user interaction with the device; the Bluetooth subsystem monitors connectivity to vehicle audio systems as a contextual indicator
    \item \textbf{Parking sign recognition}: camera enables computer vision-based extraction of parking restriction information from signage; the GPS sensor provides the location to which the sign was taken at
\end{enumerate}

This architecture aligns with established principles in smartphone-based activity recognition, where sensor diversity and information redundancy are key strategies for improving detection accuracy and fault tolerance \cite{khan2014}.


\subsubsection{GPS}

\paragraph{GPS correction}

The GPS subsystem is implemented through Flutter's geolocator package. Raw GPS coordinates suffer from several sources of error including atmospheric interference, multipath propagation in urban environments, and satellite geometry limitations. To reduce noise in GPS data, a one-dimensional Kalman filter was implemented, which processes longitude and latitude data separately (\texttt{LocationCubit}) \cite{merminod1989} -- more details are provided in Section 3.5.

The update process is triggered based on distance difference rather than time difference. This ensures that when the vehicle is stationary (e.g., waiting at a red light or parked), no unnecessary updates occur. The threshold is set to 1 metre, meaning that a new estimation is calculated only when the measured position changes by more than 1 metre.

\begin{figure}[h]

\paragraph{GPS in parking detection}

For the parking detection subsystem, GPS data undergoes sophisticated analysis to extract motion characteristics. The \texttt{GpsSpeedBloc} receives filtered coordinates from the \texttt{LocationCubit} and computes instantaneous velocity by measuring displacement between consecutive coordinate pairs using the Haversine formula (more details are provided in Section~3.5), then dividing by the elapsed time. This velocity calculation operates directly on the Kalman-filtered coordinates, eliminating the need for additional velocity filtering and avoiding the pitfall of cascaded filtering, which can introduce phase delays and distort signal characteristics.

Additionally, GPS coordinates from confirmed parking events feed a segment-based heatmap that visualizes real-time parking density across Melbourne. When users confirm parking, their location is recorded and aggregated with city sensor data to generate segment-based occupancy counts.

\paragraph{GPS in camera}

The camera-based parking sign recognition feature relies fundamentally on GPS to provide spatial context for captured signage. When a user photographs a parking sign, the \texttt{CameraBloc} queries for the current Kalman-filtered coordinates from \texttt{LocationCubit}, and attach this information with the AI-generated JSON to contribute to the restriction database.


\subsubsection{Accelerometer}


The accelerometer provides high-frequency measurements of linear acceleration along the device's three orthogonal axes ($x$, $y$, $z$), capturing the subtle vibration signature of vehicle motion. Unlike GPS, which operates at approximately one sample per second, smartphone accelerometers typically provide data at 50--100\,Hz, enabling detection of fine-grained motion patterns that would be invisible to GPS. The \texttt{AccBloc} processes this high-rate data stream through a multi-stage pipeline designed to distinguish between the characteristic vibrations of a moving vehicle and the stillness of a parked state.

After user accelerometer data (linear acceleration excluding gravity) is streamed, a 3D Kalman filter processes the raw $x$, $y$, and $z$ accelerations to reduce sensor noise. The accelerometer bloc then employs a sliding window approach with Root Mean Square (RMS) analysis -- more details provided in Section~3.5


\subsubsection{Gyroscope}

Gyroscopes enable rotation detection for vehicle motion analysis~\cite{vaiana2017}. While the accelerometer is sensitive to linear motion and vibration, the gyroscope exclusively detects rotation, making it ideal for recognizing when a driver picks up their phone to leave the car.

The \texttt{GyroBloc} implements a relatively simple processing pipeline compared to the other sensors. Raw gyroscope data undergoes 3D Kalman filtering, followed by computation of the magnitude of angular velocity. A 3-second sliding window tracks the maximum rotation magnitude observed within the window. If this maximum exceeds $0.8\,\mathrm{rad/s}$ (approximately $46^{\circ}/\mathrm{s}$), the gyroscope votes ``parked,'' interpreting the rotation spike as evidence of phone pickup.


\subsubsection{Bluetooth}

Bluetooth connectivity to vehicle audio systems (via Bluetooth or CarPlay) provides contextual evidence for motion inference: connection suggests driving, while disconnection suggests parking or vehicle exit. The implementation utilizes a custom service that polls the device's current audio output route every second.

The service detects when the device connects to or disconnects from vehicle Bluetooth or CarPlay systems. This dual detection strategy addresses a platform limitation: Flutter's native audio package does not expose a dedicated constant for CarPlay, necessitating string-based detection for CarPlay connections. This heuristic approach is robust in practice, as CarPlay connections consistently include the keyword ``CarPlay'' in their route names across iOS versions.

\subsubsection{Camera}

The camera functions as a visual sensor, capturing images of parking signs that are subsequently processed by a computer vision algorithm. This enables the system to interpret the sign’s information with respect to the user's current circumstances.

\subsection{Connectivity}

\subsubsection{Cloud Infrastructure}

ParkPie backend is deployed on Microsoft Azure Cloud in the Australia East region, utilizing two core services: Azure App Service and Azure Database for PostgreSQL 17.

\paragraph{Application tier}
The Spring Boot 3.5.4 backend runs on Azure App Service, a fully managed platform providing automatic OS patching, built-in load balancing, and integrated monitoring. Deployment uses the Azure CLI to upload JAR artifacts built with Gradle, typically completing within 2--3 minutes. The service runs on the Java 21 runtime and handles all REST API requests from mobile clients.

\paragraph{Database tier} The Azure Database for PostgreSQL stores parking signs, real-time sensor data, user sessions, and road segments. The managed service provides automated daily backups with a 7-day retention period, point-in-time restore, and SSL/TSS encrypted communication. The PostGIS extension enables efficient spatial queries, including point-in-polygon operations for density calculation and radius-based proximity searches using \texttt{ST\_DWithin}.

\paragraph{Data integration}
The backend acts as an integration hub, periodically fetching real-time parking sensor data from Melbourne City's open data API and upserting it into PostgreSQL. This centralizes data ingestion, reduces the app package size, and enables instant updates without app redeployment.

\paragraph{Security}
Database credentials are stored securely in the App Service Configuration (not hardcoded). PostgreSQL rejects non-SSL connections and restricts access to App Service IP addresses only. An admin dashboard at \texttt{/admin/login} uses basic authentication for operational tasks.

\subsubsection{API}

The application connects to cloud services hosted on Microsoft Azure, where both the database and API are deployed. Through secure HTTP requests, the frontend retrieves live data such as parking signs, active sessions, and street-segment densities. This removes the need for static or hard-coded data, letting the app reflect updates instantly when changes occur in the backend.

The system integrates multiple open datasets from the City of Melbourne, including all parking bay locations \cite{onstreet_parking_bays}, road segment maps, and parking restriction \cite{paystay_restrictions}, meter details \cite{paystay_zones_segments}, and real-time parking sensor data \cite{realtime_availability}. Road segment data from the Victorian Government \cite{road_segment_vic} is used to depict availability.

By relying on cloud APIs, the app stays synchronized with city sensors data and user activity, giving users real-time parking visibility. Centralized processing in the cloud also offloads heavy spatial and aggregation tasks from mobile devices, improving speed, lowering bandwidth use, and extending battery life.

To maintain reliability, the Azure setup supports Business Continuity and Disaster Recovery (BCP/DRP) strategies. Backup hosts and replicated databases can quickly take over if the main system fails, ensuring uninterrupted access. Together, these cloud and connectivity features make the app responsive, scalable, and resilient under real-world conditions.


\subsection{Responsiveness}

\subsubsection{Caching}

The \texttt{loadPins()} function is designed to improve app responsiveness by using a time-to-live (TTL) caching strategy. When the function is called, it first emits a loading state and checks whether cached data exists and is still valid within the given TTL (default five minutes). If the cache is fresh, it loads data directly from local storage, avoiding unnecessary network requests. This greatly reduces waiting time and ensures the interface responds quickly to user actions.

If the cache is expired or the user requests a refresh, the function fetches data from the API, saves a new copy in cache, and then emits a loaded state with the updated pins. Even if the network request fails, the app still attempts to serve data from the previous cache, maintaining usability without sudden blank screens.

The TTL value provides flexibility by allowing developers to balance between real-time accuracy and network efficiency. A shorter TTL increases freshness and responsiveness to new data but generates more network traffic, while a longer TTL reduces server requests and improves stability at the cost of slightly delayed updates. Delays are further mitigated by minimizing I/O operations and prioritizing cached responses, reducing unnecessary communication between the server and client to ensure smoother user experience.


\subsubsection{Cluster pin}

Pins clustering is done on the client but driven by server-defined “areas.” On launch, the area rectangles are fetched from the API. Each area is defined by South West/North East corners latitude and longitude; This keeps the geometry dynamic and can change boundaries in the database without shipping a new build.

Rendering is zoom-aware. When zoomed in, we place individual pins. When zoomed out, we group pins by a pin that lies inside an area’s bounding box, then render a single “cluster” marker per area with pin count. 


\subsubsection{Segment}

Segment API computes per-segment parking density on the server instead of the client. It merges two live sources, user parking sessions and city sensor “Present” statuses. Then loads the road-segment GeoJSON and derives outer rings for each Polygon/MultiPolygon. Using a point-in-polygon test, it assigns each observed vehicle location to exactly one segment and returns a compact list of \texttt{{segid, count}}.

The design moves aggregation to where the data already is. Previously, the raw location points were pushed to the frontend and counted; it took around 10 seconds due to heavy iteration, JSON transfer size, and main-thread work. Server-side mapping cuts payload size and CPU in the client, so the UI can render instantly. It also gives consistent results across devices and reduces network traffic.

There are reasonable trade-offs. While the server takes on extra computation per request, the returned density represents a real-time snapshot based on vehicles marked “Present” at that moment. Still, the approach is reliable, fast in practice, and easily cached. In the future, a caching mechanism can be added to further reduce server load and smooth out CPU peaks as user volume increases.

\subsubsection{AI Pipeline}

The Gemini workflow converts raw parking sign images into structured database entries and concise text descriptions through a multi-stage process. When a user takes a photo, the system sends it with a structured prompt enforcing strict JSON output. It retries up to three times, sanitises formatting, and validates latitude, longitude, and time before uploading. On the backend, duplicate detection (similar signs within 15m) and sequence allocation ensure data integrity. Additionally, to encourage user contributions, a second Gemini call generates a concise, context-aware summary under 120 words tailored to the user’s current situation.

\subsubsection{Security}

Security mechanism strengthens security around parking session creation, which facilitates the tracking of parking zone availability. Instead of using sequential or database-generated IDs that can be easily guessed, each session now receives a randomized identifier generated with a secure pseudo-random number and a short timestamp component. The combination of a random three-digit number, partial timestamp, and hashed app key produces a unique yet compact ID that cannot be easily inferred. This design prevents attackers from exploiting Insecure Direct Object Reference (IDOR) vulnerabilities, where predictable IDs might allow unauthorized access to other users’ sessions.

When a session is created, the system first identifies the nearest parking sign and generates the new secure session ID before inserting it into the database. The API then returns only essential information, avoiding exposure of internal IDs or unnecessary metadata.

\subsubsection{Sensors}

\paragraph{Sensor fusion mechanism}

ParkPie implements a voting-based sensor fusion algorithm where each sensor operates as an independent module that continuously analyzes its data stream and emits a categorical vote from the set {\texttt{driving}, \texttt{parked}, \texttt{unknown}}. The central \texttt{ParkingBloc} aggregates these votes using a finite state machine to determine the overall parking status.

Voting-based fusion provides several advantages:
\begin{itemize}
    \item Modularity and transparency for ease of development and debugging
    \item If one sensor fails or provides unreliable data, others compensate
    \item Sensors with different sampling rates and data types integrate seamlessly
\end{itemize}

The conditional voting logic means sensors are used selectively:

\begin{itemize}
    \item Gyroscope's votes are gated based on the current system state (during \texttt{StoppedCandidate}) as it is unreliable in other states
    \item GPS' votes are weighted based on real-time accuracy assessments
\end{itemize}

The following design decisions have been made:

\begin{itemize}
    \item The \texttt{Unknown} state serves as a conservative initialization point, preventing the system from erroneously entering Driving state due to GPS noise or brief movements when the app is launched
    \item The \texttt{Driving} state represents confirmed vehicle motion. Transition out of this state to StoppedCandidate requires convergence of GPS and accelerometer evidence: GPS must cease voting "driving" AND accelerometer must vote "parked". This conjunction ensures that brief slowdowns due to traffic or speed bumps do not trigger premature parking detection. 
    \item The \texttt{StoppedCandidate} state implements a sophisticated waiting logic with multiple exit paths, reflecting the recognition that stopping does not necessarily indicate parking (consider red lights, stop signs, or drive-through queues). Each path corresponding to a different behavioral signal: gyroscope and Bluetooth (Section~\ref{subsec:sensors}), and timeout with continued stillness is for cases where the phone is left in the vehicle. 
    \item Critically, the state machine also implements a revert path from \texttt{StoppedCandidate} back to Driving, which handles false positives from red lights or traffic congestion, and allows the system to self-correct without user intervention.
    \item Upon user confirmation, the system transitions to the terminal \texttt{Parked} state; upon user denial, it reverts to \texttt{StoppedCandidate} with reset timers, allowing re-detection if the vehicle remains stopped.



\end{itemize}

\paragraph{Kalman filter}

Kalman filtering is applied to both GPS and inertial measurement unit (IMU) data to reduce noise and produce smoother state estimates. The filter recursively combines prior estimates with new sensor readings using a \textit{predict-update} cycle based on the classical discrete-time Kalman formulation.

For each coordinate $(x, y)$ representing longitude and latitude, the estimated state is updated as:
\[
\hat{x} = \hat{x} + k(x - \hat{x}), \quad
\hat{y} = \hat{y} + k(y - \hat{y})
\]
where $x, y$ are the measured values, $\hat{x}, \hat{y}$ are the estimated values, and $k$ is the Kalman gain:
\[
k = \frac{p}{p + r}
\]
Here, $p$ denotes the estimation error (uncertainty in the estimate), and $r$ is the measurement noise. Before each update, the estimation error is predicted as:
\[
p' = p_t + q
\]
and then updated:
\[
p_{t+1} = (1 - k)p'
\]
where $q$ represents the process noise. This filtering process yields smoother and more accurate GPS trajectories by balancing prior estimates with new observations. 

For inertial sensors (IMU), consisting of accelerometer and gyroscope, Kalman filters are applied to each axis ($x$, $y$, $z$), then combined using Euclidean norm $\sqrt{x^2 + y^2 + z^2}$. The filter parameters ($q$ and $r$) are tuned differently as accelerometer has less noise compared to gyroscope. 


\paragraph{Haversine distance calculation}

To compute distances between GPS coordinates on the Earth's surface, the Haversine formula is employed. It accounts for the Earth's spherical shape, providing accurate great-circle distances compared to simple Euclidean calculations.

Given two points $(\phi_1, \lambda_1)$ and $(\phi_2, \lambda_2)$ in radians, the Haversine formula computes:

\[
a = \sin^2\Big(\frac{\phi_2 - \phi_1}{2}\Big) + \cos(\phi_1)\cos(\phi_2)\sin^2\Big(\frac{\lambda_2 - \lambda_1}{2}\Big)
\]

\[
c = 2 \, \text{atan2}(\sqrt{a}, \sqrt{1-a})
\]

\[
\text{distance} = R \, c
\]

where $R = 6371~\text{km}$ is the mean Earth radius, and $\phi, \lambda$ denote latitude and longitude, respectively. This method ensures accurate geodesic distance measurement between coordinate pairs (cf. straight-line Euclidean distance).

\paragraph{Hysteresis threshold design}

ParkPie employs hysteresis to prevent rapid state switching when sensor readings fluctuate near thresholds.

\begin{itemize}
    \item Accelerometer hysteresis: dual entry and exit thresholds create a dead zone. This Schmitt trigger logic reduces rapid toggling.
        \[
        \text{RMS: } < 0.40~\text{m/s}^2 \text{ to enter ``still'', } > 0.45~\text{m/s}^2 \text{ to exit}
        \]
        \[
        \text{Quiet ratio: } \ge 70\% \text{ to enter, } < 58\% \text{ to exit}
        \]
    \item GPS hysteresis: a single speed threshold is combined with temporal requirements. Brief speed fluctuations do not trigger state changes.
        \[
        \text{Speed threshold: } 2.78~\text{m/s}, \quad
        \text{Driving: } \ge 10~\text{s and 20~m}, \quad
        \text{Parking: } 4-6~\text{s}
        \]
    \item State machine hysteresis: The multi-state logic enforces hysteresis: minor stops require sustained conditions (gyro spike, Bluetooth disconnect, or 60~s timeout) to trigger parking detection, and once parked, sensor noise is ignored.

\end{itemize}

\paragraph{Accuracy-adaptive processing}

The GPS pipeline adapts to varying signal quality to maintain reliable detection. Fixed thresholds can fail in urban canyons, tunnels, or cold starts, so accuracy-adaptive processing is used \cite{IEEE_KalmanGPS}.  

Each GPS sample includes a horizontal accuracy estimate. The \texttt{GpsSpeedBloc} categorizes samples into three scenarios:

\begin{center}
\begin{tabular}{lccc}
\hline
Scenario & Accuracy Range & Displacement Window & Parking Confirm Time \\
\hline
Good & $\le 10$ m & 12 m & 4.0 s \\
Medium & 10--20 m & 16 m & 5.0 s \\
Poor & $>20$ m & 20 m & 6.0 s \\
\hline
\end{tabular}
\end{center}

Sample-level weighting reduces the influence of low-quality data:
\[
w = 
\begin{cases} 
1.0 & \text{if accuracy} \le 15~\text{m} \\
\text{linearly decaying to } 0.3 & \text{if accuracy} > 15~\text{m}
\end{cases}
\]

Additionally, zero-speed detection enforces $v = 0$ when $v < 0.5~\text{m/s}$ and accuracy $> 20$ m, preventing GPS drift from producing false motion signals.
