We use BLoC (Business Logic Component) state management, which is a widely adopted architecture for production-level Flutter apps. BLoC separates state, events, and business logic, allowing for clear, maintainable, and testable code.
\begin{itemize}
    \item State represents the current condition of the app.
    \item Event represents something that happens (e.g., user action or sensor update).
    \item Bloc listens to events, applies business logic, and emits new states.
\end{itemize}

BLoC exposes a stream of states, to which Flutter widgets can subscribe. For instance, in the parking detection feature, each sensor BLoC (accelerometer, gyroscope, Bluetooth, GPS) emits a sensor state. The ParkingBloc listens to these sensor states, processes votes, and emits a new ParkingState. The UI then rebuilds automatically, for example displaying a “Parking detected” popup.

This separation of concerns ensures testable components and reactive UI updates. The BLoC pattern is conceptually similar to Swift’s MVVM architecture. In cases where logic is simple, we can use the lighter-weight Cubit, which omits events and allows direct state changes.

To maintain consistent logic throughout development, we implemented unit tests for each major BLoC component: \texttt{camera}, \texttt{parking\_status\_detection}, \texttt{map}, \texttt{timer}. These tests, together with linting checks, are integrated into our CI/CD GitHub pipeline and run on every commit to ensure consistent code quality and style.

\subsubsection{Backend}

The backend is organized into clear, responsibility-focused packages: \texttt{admin}, \texttt{parking}, \texttt{core}, and \texttt{api}, keeping Spring components small, readable, and easy to navigate.

Service and repository classes use intent-revealing method names, for example:
\begin{itemize}
    \item \texttt{ParkingSignService.ingestUserSign}
    \item \texttt{ParkingRestrictionDurationService.calculateDuration}
\end{itemize}

DTOs such as \texttt{UserSignIngestDto} and \texttt{ParkingSignDto} encapsulate request and response payloads and use Jakarta validation annotations to prevent malformed data from entering the database. Non-obvious logic is documented with JavaDoc, for example:
\begin{itemize}
    \item Duplicate-detection heuristics in \texttt{ParkingSignService}
    \item Database bootstrapping and manual zone reconciliation in \texttt{DbPolishRunner} 
\end{itemize}

A comprehensive test suite ensures correctness and consistency:
\begin{itemize}
    \item Unit tests: Verify complex calculations, e.g., \texttt{ParkingRestrictionDurationServiceTest} validates time-window algorithms across edge cases.
    \item Controller tests: Assert HTTP contracts and security filters via \texttt{ParkingSignControllerTest} and \texttt{SecurityIntegrationTest}.
    \item Integration tests: Test persistence and geospatial queries against a PostGIS instance using Testcontainers, e.g., \texttt{ParkingSignRepositoryIntegrationTest} seeded with \texttt{postgis-init.sql}.
\end{itemize}
