\section{Implementation}

\subsection{Quality}

\subsubsection{Frontend}

We use BLoC (Business Logic Component) state management, which is a widely adopted architecture for production-level Flutter apps. BLoC separates state, events, and business logic, allowing for clear, maintainable, and testable code.
\begin{itemize}
    \item State represents the current condition of the app.
    \item Event represents something that happens (e.g., user action or sensor update).
    \item Bloc listens to events, applies business logic, and emits new states.
\end{itemize}

BLoC exposes a stream of states, to which Flutter widgets can subscribe. For instance, in the parking detection feature, each sensor BLoC (accelerometer, gyroscope, Bluetooth, GPS) emits a sensor state. The ParkingBloc listens to these sensor states, processes votes, and emits a new ParkingState.

This separation of concerns ensures testable components and reactive UI updates. The BLoC pattern is conceptually similar to Swift’s MVVM architecture. In cases where logic is simple, we can use the lighter-weight Cubit, which omits events and allows direct state changes. Front-end directory is organised by key features: \texttt{map}, \texttt{camera}, \texttt{parking status detection}, \texttt{timer}.

To maintain consistent logic throughout development, we implemented unit tests for each major BLoC component, using mock service where required. These tests, together with linting checks, are integrated into our CI/CD GitHub pipeline and run on every commit to ensure consistent code quality and style.

\subsubsection{Backend}

The backend is organized into clear, responsibility-focused packages: \texttt{admin}, \texttt{parking}, \texttt{core}, and \texttt{api}, keeping Spring components small, readable, and easy to navigate.

Data Transfer Objects (DTOs) such as \texttt{UserSignIngestDto} and \texttt{ParkingSignDto} encapsulate request and response payloads and use Jakarta validation annotations to prevent malformed data from entering the database. The entire backend is documented with JavaDoc, and every API endpoint has OpenAPI (Swagger) documentation.

A comprehensive test suite ensures correctness and consistency:
\begin{itemize}
    \item Unit tests: Verify complex calculations, e.g., parking restriction duration validates time-window algorithms across edge cases
    \item Controller tests: Assert HTTP contracts and security filters
    \item Integration tests: Check that data storage and location-based queries work correctly with a PostGIS database using Testcontainers.
\end{itemize}

Operations also gain leverage from the Spring Boot admin dashboard, which enables CSV imports, scheduler toggles, and live health monitoring. The dashboard offers a convenient interface for the monitoring and update of the database. \footnote{Admin portal: \url{https://parkpie-90018.azurewebsites.net/admin}\\ Username: \texttt{admin}; Password: \texttt{parkpieh1h1\#}}

\subsection{Sensors}
\label{subsec:sensors}

Sensors are used in two different scenarios:

\begin{enumerate}
    \item \textbf{Detect that a travelling vehicle has parked}: GPS sensor provides macroscopic motion information through velocity and displacement measurements; the accelerometer captures microscopic vibration patterns that distinguish driving from stationary states; the gyroscope detects rotational signatures indicating user interaction with the device; the Bluetooth subsystem monitors connectivity to vehicle audio systems as a contextual indicator
    \item \textbf{Parking sign recognition}: camera enables computer vision-based extraction of parking restriction information from signage; the GPS sensor provides the location to which the sign was taken at
\end{enumerate}

This architecture aligns with established principles in smartphone-based activity recognition, where sensor diversity and information redundancy are key strategies for improving detection accuracy and fault tolerance \cite{khan2014}.


\subsubsection{GPS}

\paragraph{GPS correction}
The GPS subsystem uses Flutter’s geolocator package. Raw coordinates are affected by errors from atmospheric interference, multipath propagation, and satellite geometry. A one-dimensional Kalman filter \cite{merminod1989} processes longitude and latitude separately (\texttt{LocationCubit}) to reduce noise [Section 3.5].

Updates are triggered by distance changes ($>$1m) rather than time, avoiding unnecessary updates when stationary (e.g., waiting at a red light or parked).

    \centering

\paragraph{GPS in parking detection}
For parking detection, GPS data is analysed to extract motion characteristics. The \texttt{GpsSpeedBloc} receives Kalman-filtered coordinates from the \texttt{LocationCubit} and computes instantaneous velocity using displacement between consecutive points via the Haversine formula (Section 3.5) divided by elapsed time. This avoids additional velocity filtering and the phase delays caused by cascaded filters. Confirmed parking events contribute GPS coordinates to a segment-based heatmap, combining user and city sensor data to visualise real-time parking density.

\paragraph{GPS in camera}

The camera-based parking sign recognition feature relies fundamentally on GPS to provide spatial context for captured signage. When a user photographs a parking sign, the \texttt{CameraBloc} queries for the current Kalman-filtered coordinates from \texttt{LocationCubit}, and attach this information with the AI-generated JSON to contribute to the restriction database.


\subsubsection{Accelerometer}

The accelerometer provides high-frequency measurements of linear acceleration along the device's three orthogonal axes ($x$, $y$, $z$), capturing the subtle vibration signature of vehicle motion. Unlike GPS, which operates at approximately one sample per second, smartphone accelerometers typically provide data at 50--100\,Hz, enabling detection of fine-grained motion patterns that would be invisible to GPS. The \texttt{AccBloc} processes this high-rate data stream through a multi-stage pipeline designed to distinguish between the characteristic vibrations of a moving vehicle and the stillness of a parked state.

After user accelerometer data (linear acceleration excluding gravity) is streamed, a 3D Kalman filter processes the raw $x$, $y$, and $z$ accelerations to reduce sensor noise. The accelerometer bloc then employs a sliding window approach with Root Mean Square (RMS) analysis -- more details provided in Section~3.5


\subsubsection{Gyroscope}

Gyroscopes enable rotation detection for vehicle motion analysis~\cite{liu2017}. While the accelerometer is sensitive to linear motion and vibration, the gyroscope exclusively detects rotation, making it ideal for recognizing when a driver picks up their phone to leave the car.

The \texttt{GyroBloc} implements a relatively simple processing pipeline compared to the other sensors. Raw gyroscope data undergoes 3D Kalman filtering, followed by computation of the magnitude of angular velocity. A 3-second sliding window tracks the maximum rotation magnitude observed within the window. If this maximum exceeds $0.8\,\mathrm{rad/s}$ (approximately $46^{\circ}/\mathrm{s}$), the gyroscope votes ``parked,'' interpreting the rotation spike as evidence of phone pickup.


\subsubsection{Bluetooth}

Bluetooth connectivity to vehicle audio systems (via Bluetooth or CarPlay) provides contextual evidence for motion inference: connection suggests driving, while disconnection suggests parking or vehicle exit. The implementation utilizes a custom service that polls the device's current audio output route every second.

The service detects when the device connects to or disconnects from vehicle Bluetooth or CarPlay systems. This dual detection strategy addresses a platform limitation: Flutter's native audio package does not expose a dedicated constant for CarPlay, necessitating string-based detection for CarPlay connections. This heuristic approach is robust in practice, as CarPlay connections consistently include the keyword ``CarPlay'' in their route names across iOS versions.

\subsubsection{Camera}

The camera functions as a visual sensor, capturing images of parking signs that are subsequently processed by a computer vision algorithm (Google Gemini). This enables the system to interpret the sign’s information with respect to the user's current circumstances.

\subsection{Connectivity}

\subsubsection{Cloud Infrastructure}

ParkPie backend is deployed on Microsoft Azure Cloud in the Australia East region, utilizing two core services: Azure App Service and Azure Database for PostgreSQL 17.

\begin{itemize}
    \item \textbf{Application tier}: The Spring Boot 3.5.4 backend runs on Azure App Service, a fully managed platform providing automatic OS patching, built-in load balancing, and integrated monitoring. Deployment uses the Azure CLI to upload JAR artifacts built with Gradle, typically completing within 2--3 minutes. The service runs on the Java 21 runtime and handles all REST API requests from mobile clients.

\item \textbf{Database tier}: The Azure Database for PostgreSQL stores parking signs, real-time sensor data, user sessions, and road segments. The managed service provides automated daily backups with a 7-day retention period, point-in-time restore, and SSL/TSS encrypted communication. The PostGIS extension enables efficient spatial queries, including point-in-polygon operations for density calculation and radius-based proximity searches using \texttt{ST\_DWithin}.
\item \textbf{Data integration}:
The backend acts as an integration hub, periodically fetching real-time parking sensor data from Melbourne City's open data API and upserting it into PostgreSQL. This centralizes data ingestion, reduces the app package size, and enables instant updates without app redeployment.
\item \textbf{Security}: Database credentials are stored securely in the App Service Configuration (not hardcoded). PostgreSQL rejects non-SSL connections and restricts access to App Service IP addresses only. An admin dashboard at \texttt{/admin/login} uses basic authentication for operational tasks.
\end{itemize}

\subsubsection{API}

The application connects to cloud services hosted on Microsoft Azure, where both the database and API are deployed.

The system integrates multiple open datasets from the City of Melbourne, including all parking bay locations \href{https://data.melbourne.vic.gov.au/explore/dataset/on-street-parking-bays/information/}{on-street parking bays}, \href{https://data.melbourne.vic.gov.au/explore/dataset/pay-stay-parking-restrictions/information/}{parking restrictions} , \href{https://data.melbourne.vic.gov.au/explore/dataset/pay-stay-zones-linked-to-street-segments/information/}{meter details}, and \href{https://data.melbourne.vic.gov.au/explore/dataset/on-street-parking-bay-sensors/information/}{real-time parking sensor data}. \href{https://discover.data.vic.gov.au/dataset/road-segment}{Road segment data} from the Victorian Government is used to depict availability.

By relying on cloud APIs, the app stays synchronized with city sensors data and user activity, giving users real-time parking visibility. Centralized processing in the cloud also offloads heavy spatial and aggregation tasks from mobile devices, improving speed, lowering bandwidth use, and extending battery life.

To maintain reliability, the Azure setup supports Business Continuity and Disaster Recovery (BCP/DRP) strategies. Backup hosts and replicated databases can quickly take over if the main system fails, ensuring uninterrupted access. 

\subsubsection{Crowdsourced Information}

A key source of information for the app comes from its users. To the best of our knowledge, there is no centralised record of all parking restrictions in Victoria. Some councils (e.g., the City of Melbourne) voluntarily publish this information, but each does so in a different format. Alternatively, services such as EasyPark and PayStay provide parking data, though only for their own proprietary zones. By exploiting user-contributed data, we aim to build a more comprehensive database of parking restrictions. This crowdsourced model has proven successful in other applications, such as \href{https://www.waze.com/en-GB/live-map}{Waze} and \href{https://petrolspy.com.au/map/latlng/-33.8657305/151.20733}{PetrolSpy}.

\subsection{Responsiveness}

\subsubsection{Caching}

The \texttt{loadPins()} function is designed to improve app responsiveness by using a time-to-live (TTL) caching strategy. When the function is called, it first emits a loading state and checks whether cached data exists and is still valid within the given TTL (default five minutes). If the cache is fresh, it loads data directly from local storage, avoiding unnecessary network requests. This greatly reduces waiting time and ensures the interface responds quickly to user actions.

If the cache is expired or the user requests a refresh, the function fetches data from the API, saves a new copy in cache, and then emits a loaded state with the updated pins. Even if the network request fails, the app still attempts to serve data from the previous cache, maintaining usability without sudden blank screens.

The TTL value provides flexibility by allowing developers to balance between real-time accuracy and network efficiency. A shorter TTL increases freshness and responsiveness to new data but generates more network traffic, while a longer TTL reduces server requests and improves stability at the cost of slightly delayed updates. Delays are further mitigated by minimizing I/O operations and prioritizing cached responses, reducing unnecessary communication between the server and client to ensure smoother user experience.


\subsubsection{Cluster pin}

Pins clustering is done on the client but driven by server-defined “areas.” On launch, the area rectangles are fetched from the API. Each area is defined by South West/North East corners latitude and longitude; This keeps the geometry dynamic and can change boundaries in the database without shipping a new build.

Rendering is zoom-aware. When zoomed in, we place individual pins. When zoomed out, we group pins by a pin that lies inside an area’s bounding box, then render a single “cluster” marker per area with pin count. 


\subsubsection{Segment}

The Segment API computes per-segment parking density on the server by merging live user parking sessions and city sensor “Present” data. It loads the road-segment GeoJSON, extracts polygon rings, and uses point-in-polygon tests to assign each vehicle to a segment, returning a compact list of \texttt{{segid, count}}.

This design shifts aggregation to the server, avoiding heavy frontend iteration and large JSON transfers. Processing time drops from about 10 seconds to near-instant rendering, while ensuring consistent results and reduced client CPU and network load.

Though the server now handles more computation per request, it delivers real-time density snapshots efficiently. The approach is reliable, scalable, and can be further optimised with caching to smooth CPU peaks as traffic grows.

\subsubsection{AI Pipeline}

The Gemini workflow converts parking sign photos into structured database entries and concise summaries. Photos are sent with a JSON prompt, retried up to three times, validated, and uploaded. Backend duplicate detection (within 15m) and sequence allocation ensure data integrity, while a second call generates context-aware summaries--with reference to user's location and date/time--to encourage user contributions.

\subsubsection{Security}

The security mechanism strengthens parking session creation by assigning each session a randomized ID combining a three-digit random number, partial timestamp, and hashed app key. This prevents attackers from exploiting predictable IDs (IDOR). When a session is created, the system identifies the nearest parking sign, generates the secure ID, inserts it into the database, and returns only essential information to avoid exposing internal IDs or metadata.

\subsubsection{Sensors}

\paragraph{Sensor fusion mechanism}

ParkPie uses a voting-based sensor fusion algorithm where each sensor independently votes \texttt{driving}, \texttt{parked}, or \texttt{unknown}. The central \texttt{ParkingBloc} aggregates votes via a finite state machine to determine overall parking status.

Voting-based fusion ensures modularity, transparency, and robustness—other sensors compensate if one fails, and sensors with different types and rates integrate seamlessly. Conditional logic weights or gates votes (e.g., gyroscope used only during \texttt{StoppedCandidate}, GPS weighted by accuracy).
Key state machine design:
\begin{itemize}
    \item \texttt{Unknown}: conservative start to avoid false driving detection.
    \item \texttt{Driving}: confirmed motion; exit requires both GPS and accelerometer evidence.
    \item \texttt{StoppedCandidate}: handles temporary stops (red lights, queues) with multiple exit paths and a revert to \texttt{Driving} for false positives.
    \item \texttt{Parked}: terminal state reached upon user confirmation; denial reverts to \texttt{StoppedCandidate} for re-detection.
\end{itemize}
\begin{figure}[h]
    \centering

    \caption{Flow chart of sensor fusion mechanism}

The conditional voting logic means sensors are used selectively:

\begin{itemize}
    \item Gyroscope's votes are gated based on the current system state (during \texttt{StoppedCandidate}) as it is unreliable in other states
    \item GPS' votes are weighted based on real-time accuracy assessments
\end{itemize}


\paragraph{Kalman filter}

Adaptive Kalman filtering \cite{kalman1960, mohamed1999adaptive} is applied to both GPS and inertial measurement unit (IMU) data to reduce noise and produce smoother state estimates. 
For each coordinate $(x, y)$, the state is updated as:
\[
\hat{x} = \hat{x} + k(x - \hat{x}), \quad
\hat{y} = \hat{y} + k(y - \hat{y})
\]
where $x$ and $y$ are the measured values, $\hat{x}$ and $\hat{y}$ are the estimated values, and $k$ is the Kalman gain. 
Unlike the standard implementation, the adaptive version dynamically adjusts the process noise $q$ and measurement noise $r$ based on recent innovation statistics, allowing the filter to respond to changing noise conditions and improve estimation stability. 
Full implementation details are provided in Appendix~6.1.6.

\paragraph{Haversine distance calculation}

To compute distances between two GPS coordinates $(\phi_1, \lambda_1)$ and $(\phi_2, \lambda_2)$ (in radians), the Haversine formula is used:

\[
a = \sin^2\Big(\frac{\phi_2 - \phi_1}{2}\Big) + \cos(\phi_1)\cos(\phi_2)\sin^2\Big(\frac{\lambda_2 - \lambda_1}{2}\Big),\text{distance} = 2R \text{ atan2}(\sqrt{a}, \sqrt{1-a})
\]

This accounts for the Earth’s curvature and provides accurate geodesic distances. Full derivation and threshold details are provided in Appendix 6.1.6.

\paragraph{Hysteresis threshold design}
ParkPie uses hysteresis to prevent rapid state switching near thresholds. Accelerometer, GPS, and state machine readings all employ entry/exit logic to reduce false triggers.
\paragraph{Accuracy-adaptive processing}

The GPS pipeline adapts to varying signal quality to maintain reliable detection. Fixed thresholds can fail in urban canyons, tunnels, or cold starts, so accuracy-adaptive processing is used \cite{IEEE_KalmanGPS}.  

Each GPS sample includes a horizontal accuracy estimate. The \texttt{GpsSpeedBloc} categorizes samples into three scenarios:

\begin{center}
\begin{tabular}{lccc}
\hline
Scenario & Accuracy Range & Displacement Window & Parking Confirm Time \\
\hline
Good & $\le 10$ m & 12 m & 4.0 s \\
Medium & 10--20 m & 16 m & 5.0 s \\
Poor & $>20$ m & 20 m & 6.0 s \\
\hline
\end{tabular}
\end{center}

Sample-level weighting reduces the influence of low-quality data:
\[
w = 
\begin{cases} 
1.0 & \text{if accuracy} \le 15~\text{m} \\
\text{linearly decaying to } 0.3 & \text{if accuracy} > 15~\text{m}
\end{cases}
\]

Additionally, zero-speed detection enforces $v = 0$ when $v < 0.5~\text{m/s}$ and accuracy $> 20$ m, preventing GPS drift from producing false motion signals.
